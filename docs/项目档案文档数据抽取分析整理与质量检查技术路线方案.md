# 项目档案文档数据抽取分析整理与质量检查技术路线方案

## 一、项目概述与目标

### 1.1 项目背景

针对工程类项目档案（包含数百个PDF、图片文件及待验证Excel文件），构建一套高效的数据抽取、分析整理与质量检查系统。核心挑战在于处理复杂版式文档中的非结构化信息，并在本地部署约束下实现高性能、高准确率的信息提取。

### 1.2 核心目标

- 高效处理数百个工程类文档（PDF/图片）
- 精准提取复杂版式、表格中的特定内容
- 验证文档齐备性（环评报告、验收报告等）
- 检查签字、盖章完整性
- 支持本地化部署与成本控制

### 2.2 技术架构先进性与通用性评估

#### 关于Palantir本体论技术框架的评估

| 维度 | Palantir本体论 | 本方案采用 |
|------|---------------|-----------|
| 核心思想 | 基于本体的知识图谱构建 | 基于LLM的语义理解+规则引擎 |
| 实施成本 | 高（需构建完整本体） | 中（基于提示词工程+微调） |
| 灵活性 | 中（本体变更成本高） | 高（提示词即可调整） |
| 工程文档适配 | 需大量定制本体 | 直接利用LLM理解能力 |
| 本地化部署 | 不支持 | 支持 |

**结论**：不直接采用Palantir本体论框架，而是采用**"LLM语义理解 + 可配置规则引擎 + 向量化检索"**的轻量级方案，原因如下：

1. 工程类文档类型多样，构建完整本体成本过高
2. LLM已具备强大的语义理解能力，可直接理解文档类型和要素
3. 规则引擎可灵活配置检查标准（如四性检测规则）
4. 向量化检索支持相似文档匹配和模板复用

## 三、文档处理与信息抽取技术方案

### 3.1 文档处理流水线

```
输入文档 (PDF/图片/Excel)
    ↓
┌─────────────────┐
│ 1. 文档分类与路由 │ ← LLM/VLM快速分类文档类型
└─────────────────┘
    ↓
┌─────────────────┐
│ 2. 版面分析(Layout)│ ← PP-DocLayout/DocLayout-YOLO
│   - 检测表格区域  │
│   - 检测标题区域  │
│   - 检测正文区域  │
│   - 检测印章区域  │
└─────────────────┘
    ↓
┌─────────────────┐
│ 3. OCR文字识别   │ ← PP-OCRv4 / RapidOCR
│   - 印刷体识别   │
│   - 手写体识别   │
│   - 表格结构识别 │
└─────────────────┘
    ↓
┌─────────────────┐
│ 4. 要素提取      │ ← LLM结构化提取
│   - 题名/责任者  │
│   - 文号/日期    │
│   - 签字/盖章检测│
└─────────────────┘
    ↓
┌─────────────────┐
│ 5. 质量检查      │ ← 规则引擎+LLM推理
│   - 文档齐备性   │
│   - 内容一致性   │
│   - 格式合规性   │
└─────────────────┘
    ↓
结构化结果 + 质量报告
```

### 3.2 复杂信息抽取策略

#### 3.2.1 文档齐备性检查（清单核对）

采用**双轨验证机制**：

| 检查项 | 技术方案 | 实现方式 |
|--------|---------|---------|
| 必备文档清单 | 规则引擎 | 预置工程档案必备文档类型清单 |
| 文档类型识别 | LLM分类 | 通过文档标题/内容识别文档类型 |
| 缺失检测 | 集合比对 | 实际文档集合 vs 标准清单 |

**示例检查清单**：
- 立项批复文件
- 环评报告
- 土地使用证
- 规划许可证
- 施工许可证
- 竣工验收报告
- 质检报告

#### 3.2.2 签字盖章完整性检查

| 检查项 | 技术方案 | 模型/工具 |
|--------|---------|----------|
| 印章检测 | 目标检测 | PP-OCRv4_mobile_seal_det |
| 签名检测 | 目标检测 + 分类 | 自定义签名检测模型 |
| 印章识别 | OCR + 规则 | 印章文字OCR识别 |
| 盖章位置验证 | Layout分析 | 检测盖章是否在指定区域 |

#### 3.2.3 材料完整性检查

```python
# 检查逻辑示例
def check_material_completeness(document_text, required_materials):
    """
    利用LLM判断文档中提到的材料是否完整
    """
    prompt = f"""
    请检查以下工程文档中提到的各类材料是否完整：

    文档内容：{document_text}

    标准材料清单：
    {required_materials}

    请返回JSON格式：
    {{
      "materials_found": ["材料1", "材料2"],
      "materials_missing": ["缺失材料1"],
      "completeness_rate": 0.85,
      "issues": ["问题描述"]
    }}
    """
    return llm_analyze(prompt)
```

## 四、LLM应用策略

### 4.1 LLM应用场景矩阵

| 应用场景 | 使用方式 | 模型要求 | 输入/输出 |
|----------|---------|----------|-----------|
| 文档分类 | 单轮推理 | 7B+ | 文档OCR文本 → 文档类型 |
| 要素提取 | 结构化提示词 | 7B+ | OCR文本+要素列表 → JSON |
| 内容一致性检查 | 比对推理 | 13B+ | 两份文本 → 一致性判断 |
| 文档齐备性判断 | 清单核对 | 7B+ | 文档列表+标准清单 → 缺失项 |
| 表格内容理解 | 结构化提取 | 13B+ | 表格文本 → 结构化数据 |
| 签字盖章检测 | VLM视觉分析 | 多模态7B+ | 图像 → 检测结果 |
| 质量报告生成 | 文本生成 | 7B+ | 检查结果 → 自然语言报告 |

### 4.2 提示词工程策略

#### 4.2.1 要素提取提示词模板

```

【输出格式】
{
  "title": "...",

  "date": "..."
}
```

```
【标准规则】{rules}

【输出要求】
返回JSON格式：
```

### 4.3 LLM结果可靠性保障

| 策略 | 说明 |
|------|------|
| 多模型投票 | 对关键字段使用多个LLM提取，取多数结果 |
| 置信度阈值 | 设置OCR置信度阈值（默认0.5），低置信度标记人工复核 |
| 规则校验 | LLM提取结果经规则引擎二次校验（如日期格式、文号格式） |
| 人工复核标记 | 低置信度或冲突结果自动标记待复核 |

## 六、多模态信息提取评估

### 6.1 可行性评估

| 应用场景 | 可行性 | 优势 | 劣势 | 推荐度 |
|----------|--------|------|------|--------|
| 文档分类 | ★★★★★ | 直接理解版面布局 | 需大量训练数据 | 推荐 |
| 印章检测 | ★★★★☆ | 端到端检测+识别 | 小目标检测难度大 | 推荐 |
| 签名检测 | ★★★☆☆ | 视觉特征直接提取 | 准确率待验证 | 谨慎 |
| 表格提取 | ★★★★☆ | 理解表格结构 | 复杂表格易出错 | 推荐 |
| 图纸识别 | ★★☆☆☆ | 可识别图纸类型 | 技术细节识别差 | 不推荐 |
| 手写体识别 | ★★★☆☆ | 端到端识别 | 准确率低于专用OCR | 谨慎 |

### 6.2 实施路径

#### 第一阶段：文本为主+视觉辅助（POC阶段）

```
文档图像 → OCR提取文本 → LLM文本分析（主）
    ↓
印章/签名区域 → VLM视觉检测（辅）
```

- 主要依赖OCR+LLM文本分析
- 印章检测使用专用视觉模型
- 多模态LLM仅用于文档分类和版面理解

#### 第二阶段：多模态融合（生产阶段）

```
文档图像 ──┬──► VLM理解版面结构 ──┐
           │                       ├──► 融合推理 ──► 结果
           └──► OCR提取文本 ──────┘
```

- 引入多模态LLM（如Qwen-VL、InternVL）
- 视觉信息与文本信息融合推理
- 提升复杂版式文档理解能力

### 6.3 多模态模型选型

| 模型 | 参数量 | 显存需求 | 特点 | 适用场景 |

| Qwen2-VL-7B | 7B | 16GB | 中文优化好 | 文档分类、版面分析 |

| MiniCPM-V-2.6 | 8B | 16GB | 高效轻量 | 印章检测、签名识别 |

## 九、总结

本方案基于现有Ruyi-AIMP和OpenRefine技术栈，设计了完整的项目档案文档数据抽取、分析整理与质量检查技术路线：

1. **技术架构**：采用分层架构，LLM语义理解+规则引擎替代重型本体论框架，兼顾先进性与实用性
2. **信息抽取**：OCR+Layout分析+LLM结构化提取的流水线，针对工程文档特点优化
3. **LLM应用**：明确7大应用场景，提示词工程保障提取质量
4. **部署方案**：提供纯本地、私有云混合、公有云混合三种方案，POC推荐纯本地部署
5. **多模态评估**：POC阶段以文本为主、视觉为辅，生产阶段逐步引入多模态融合
6. **POC计划**：8周分4阶段实施，总预算15.3万元，团队7人

该方案充分利用现有技术积累（PP-OCR、OpenRefine插件体系、AIMP服务框架），在本地化部署约束下实现高效、准确的档案文档智能处理。
