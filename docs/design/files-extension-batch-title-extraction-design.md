## 1. 需求分析

### 1.1 需求背景

FilesExtension 第一版已实现"文件夹元数据导入 + 同步信息提取"（提取完成后一次性生成多 Sheet 项目）。在档案数字化著录场景下，一个文件夹可能包含数百个图像子文件夹/PDF，逐个 OCR+LLM 提取耗时较长（单单元约 10~60 秒），同步模式会导致用户在导入界面长时间等待，且预览界面无法承载长时间的提取任务。

因此需要将模式升级为：**先快速创建空项目（仅列头），立即进入项目视图，随后后台批量提取、按提取进度逐行增量填充数据**，用户全程可见进度并可即时对已提取行进行复核编辑。

同时，用户需要灵活控制 LLM 的提取内容范围（增加或排除特定要素类型），故引入自定义提取类型能力。案卷模式（按卷整理的目录组织）已在需求中提出，经 r2/r3 评审恢复至本期并定为**首要实现目标**（第一落地场景：法院卷宗材料整理），权威设计见 4.7。

### 1.2 原始需求描述

**第一轮**：

> 将 FilesExtension 扩展成自动批量提取文件夹中图像/PDF 文件的标题功能，按照：**文件夹名、件号、起止页号、页数、题名、责任者、文号、成文日期、文件夹路径** 这些字段自动提取成符合 OpenRefine 数据文件格式的数据，可以按照流程直接创建项目；**先创建空项目，然后再在空项目中，随着数据提取进度，自动把数据按行进行增加填充**。

**第二轮（v1.1 新增）**：

> 1、提取模式有两种：**案件、案卷**；默认为案件方式，即根目录下为 1）件文件夹，件文件夹下为当前件的图像/pdf，或 2）pdf，一个 pdf 为一件（即所有图片在一个 pdf 中）。
> 2、提取内容可自定义：openrefine 侧可设置自定义提示词，方便用户自定义（主要为自定义提取类型），可以定义两种操作：**增加、排除**；比如增加、排除某种（身份证、证据）提取类型；设定完成后 AIMP 可按自定义进行提示词调整提取内容。

### 1.3 需求理解与澄清（含评审结论）

| 编号 | 理解 | 说明 |
|------|------|------|
| U-1 | "复核openrefine数据文件格式" 理解为 "**符合** OpenRefine 项目数据格式" | 即提取结果组装为 OpenRefine 列/行结构，走现有导入流程直接创建项目 |
| U-2 | "标题功能" 扩展为结构化著录要素提取 | 题名为核心，同时提取责任者、文号、成文日期（与现有 key_list 一致） |
| U-3 | 提取粒度：案件模式下最小单元 = 件文件夹 或 单个 PDF | 每件一行 |
| U-4 | 空项目 = 仅含列模型（表头）、0 行数据 | 创建后即注册为正式项目，可立即跳转项目视图 |
| U-5 | 本期为新建著录场景，不含档号列 | 第一版 ARCHIVE_CASE/ARCHIVE_VOLUME 模板保留，新增独立模板 |
| U-6 | **案件模式（本期保留实现，优先级降低）**：根目录下每个"含图像或PDF的子文件夹"为一件；根目录下每个 PDF 文件为一件 | 一件一行 |

### 1.8 评审意见（需求与字段）

**【R-01｜P0】扫描深度未定义**
- 问题：1.3 U-6 与 4.1.3 仅扫描根目录下一级（根下件文件夹/PDF）。实际档案整理目录常为"全宗/目录/件"或"年度/月份/件"，多级结构下扫描结果为空，且用户在导入页无法自诊断。
- 影响：功能不可用（0 件）或用户误判目录内容错误，属需求边界缺失。
- 建议：① 明确本期支持的目录深度；② 若支持多级，导入页增加"件层深度"选择（如"根下第 N 层为件"）；③ 0 件时给出目录结构诊断提示（列出扫描到的层级与前若干目录名）。
- 闭环要求：业务确认目录组织形态；如需多级，更新 4.1.3 与 4.5.1。

**【R-02｜P0】"提取状态"列语义与用法自相矛盾**
- 问题：1.5 定义状态列取值仅"成功/失败/部分提取"三值；但 4.1.5、第 5 节多处要求"失败原因写入状态列""状态列标注页数未知""状态列标注日期未规范化""状态列标注自定义要素未提取"。同一列既作枚举又作自由文本，将破坏筛选、统计与后续自动化校验。
- 影响：数据口径不一致，复核流程（FR-7）无法依赖固定枚举。
- 建议：拆为两列——"提取状态"（枚举：成功/部分提取/失败/已取消）+ "备注"（自由文本：失败原因、页数未知、日期未规范化、自定义要素缺失等）。列结构由 10 列调整为 11 列。
- 闭环要求：确认列结构变更，并同步修订 1.5、4.1.1 模板列数组、4.1.5、第 5 节、第 6 节国际化键（含 R-25 的部分提取口径）。
- **【闭环｜2026-09-17｜v1.6】定稿拆两列**（提取状态枚举 + 备注）；1.5 案件模式已更新（去起止页号 + 备注列，共 10 列），4.7.3 案卷列结构同步（11 列）。

**【R-03｜P1】件号解析规则过简且无重复检测**
- 问题：4.4.1"第一段连续数字"在 `2024年003号文件夹` 场景解析为 2024（业务期望 3），`X办函〔2024〕1号` 命名同理；且未处理两件解析出相同件号（如 `001号` 与 `001卷`）。
- 建议：改为"取末段连续数字"或提供"首段/末段"选项；导入页预览中展示全部件的解析结果并高亮重复件号，重复时提示可回退顺序号。
- 闭环要求：业务确认取段规则；实现补充重复检测与预览交互。

**【R-04｜P1】"文件夹名"与"件号"列信息冗余**
- 问题：文件夹名 `003号文件夹` 与件号 `3` 同源；1.5 已独立设置"文件夹路径"列，文件夹名的定位作用有限，案卷模式降级后冗余更明显。
- 建议：确认保留必要性（若用于批量人工比对可保留），或改为"件名称"（PDF 场景下具独立价值）。

**【R-05｜P1】"起止页号"件级语义待确认**
- 问题：件级著录通常以"页数"表达篇幅，"起止页号"多用于卷内件之间的连续编号。当前 folder 由图像文件名解析、pdf 固定 `1-页数`，与"页数"列高度重合；另多页 tif（单文件多页）会使"文件数≠页数"，导致起止页号与页数不一致。
- 建议：业务确认件级是否需要"起止页号"；确认实际数据是否存在多页 tif；若存在，4.4.2/4.4.3 需统一由页数口径推导并说明失真范围。

**【R-06｜P2】成文日期存储类型未定义**
- 问题：4.3.3 规定规范化为 `yyyy-MM-dd`，但未说明在 OpenRefine Cell 中以字符串还是日期值存储，影响排序、时间轴与后续数据校验。
- 建议：本期统一按字符串存入（与现有 `new Cell(value, null)` 组装方式一致），并在文档中显式说明，避免实现分歧。

### 3.2 关键设计决策

| 编号 | 决策 | 理由 |
|------|------|------|
| D-1 | **增量填充直接操作 `SheetData.rows`（追加 Row），不走 History/Change 机制** | 提取数据是"导入数据"而非"用户操作"，无撤销语义；rows 为可变列表，追加成本最低；`GetRowsCommand` 直接读 project.rows。与第一版组装 SheetData 方式一致，仅从"一次性填充"改为"逐行追加" |
| D-2 | **后台任务自建 `BatchExtractionManager`（静态单例 + 有界线程池），不注册为 OpenRefine Process** | ① 提取由网络 IO 主导、耗时分钟级，ProcessManager 队列串行且与项目生命周期耦合；② 自建管理器跨 ImportingJob/Project 生命周期存续，天然支持"创建项目后继续填充"；③ 进度数据结构更丰富。进度展示通过专用命令轮询（D-4） |
| D-3 | **先建空项目再提取（而非提取完再建项目）** | 用户核心需求；项目立即可见，用户可对已落表行即时复核编辑 |
| D-4 | **新增专用进度命令 `get-extraction-progress`，前端自建轻量进度条** | 进度需展示"当前正在提取的文件名、成功/失败计数"等业务信息；备选复用 get-processes（改动更小但表达力差），本期采用自建命令 |
| D-5 | **持久化节流 + 任务结束强制保存** | 每行保存一次 IO 压力大；默认每 10 行或 30s 保存一次（NFR-4），OpenRefine 全局定时保存兜底 |
| D-6 | **提取结果行追加与用户编辑共存；提取中禁用列结构变更** | 行追加只发生在尾部，不影响已落表行的编辑；增删列/改列名与追加冲突，提取中前端置灰 |
| D-7 | **AIMP 调用沿用 `/extract/upload` 逐单元同步模式，本期不依赖 batch_extract** | 客户端已实现；并行度由 Java 线程池控制。batch_extract 作为后续性能优化项 |
| D-8 | **提取模式实现为模板级差异；本期仅实现案件模式，案卷模式整体降级后续版本** | 评审结论 Q-9/Q-11/Q-12；案卷的两级扫描、条目类型列、汇总行设计保留在文档中（4.1.3/4.2），后续启用时按此实现 |
| D-9 | **自定义提取类型以结构化 JSON 传递（name/action/description），AIMP 端负责提示词组装与返回 key 对齐** | 符合 U-9（OpenRefine 不拼 LLM 提示词）；现有 `AimpLlmClient.extractContent` 将 results 的 key/value 全量放入 map，自定义类型列按"列名=类型名"直接取值即可，无需改映射机制 |
| D-10 | **动态列在空项目创建时一次性确定** | 自定义配置发生在导入页（创建项目之前），创建时即可固化列结构；提取过程中列结构不再变化（与 D-6 一致） |

### 3.3 评审意见（架构与决策）

**【R-07｜P0】后台追加 rows 与 OpenRefine Change 机制存在并发冲突**
- 问题：D-1 让后台线程直接 `sheetData.rows.add(row)`，D-6 仅要求"前端置灰列结构操作"。但 OpenRefine 的 Change（编辑单元格、批量表达式、排序、移列、星标、以及基于筛选结果的批量操作）在 apply 时会遍历/改写 `project.rows`：① 与追加线程并发可能抛并发修改异常或产生不一致状态；② 排序/重排类 Change 会使后续追加行的插入位置不可预期；③ 用户在提取中对已完成行的编辑与后台"落表"动作可能相互影响。
- 影响：存在数据错乱风险（P0）；且按 D-6 仅在提取中禁用列结构操作，用户在提取中实际无法安全执行任何数据操作，与"边提取边复核"（FR-5）的体验假设不符。
- 建议（二选一，评审选定）：
  - **方案甲（推荐，改动小）**：提取期间项目只读——后端在命令分发层拦截 Change 类操作并返回"提取进行中"提示，前端置灰全部数据操作入口（非仅列结构），进度条旁提示"提取完成后可编辑"。
  - **方案乙（体验最好，改动大）**：影子 Sheet + 完成合并——提取结果先写入不对外可见的暂存 SheetData/内存缓冲（用户界面仅展示进度），任务完成后一次性以 Change 合并到目标 Sheet。此时数据进入 History（可撤销），且与用户编辑的互斥由 History 机制天然保证；代价是用户无法"边提取边复核"（与 FR-5 部分冲突）。
- 闭环要求：明确选定方案，并同步修订 D-1、D-6、4.5.2、第 9 节风险表。
- **【闭环｜2026-09-17｜v1.6】选定方案甲**：提取期项目只读——后端拦截 Change 类操作（提示"提取进行中"），前端置灰全部数据操作入口；白名单：浏览、只读筛选/切面、导出（4.5.2 已同步）。

**【R-08｜P0】追加行未定义行模型同步动作**
- 问题：D-1/4.1.5 仅描述 `rows.add(row)`，但 OpenRefine 行模型不止 rows：`ColumnModel`（列数/maxCellIndex）、行数统计、`recordModel`（记录边界，记录模式与 CSV/TSV 导出依赖）均需同步。仅追加 rows 可能导致记录模式错乱或导出异常。
- 建议：定义"标准行追加动作"清单：追加 Row → 同步列模型可见范围 → 按单行记录追加记录边界（无分组诉求时与 `SeparatorBasedImporter` 的建行结果对齐）。实现前对照 `ImportingParserBase`/`SeparatorBasedImporter` 的实际建行与 recordModel 处理方式。
- 闭环要求：补充实现清单，集成测试覆盖"记录模式切换 + CSV 导出正确性"。

**【R-12｜P2】进度抽象与现有进程机制不统一**
- 问题：D-4 自建 `get-extraction-progress`，与 OpenRefine 既有 `get-processes`/ProcessPanel 抽象并存，前端取消交互与错误提示需重复实现。
- 建议：保留 D-4（业务表达力优先），但进度返回结构尽量对齐 Process 的字段命名（state/progress/done 等），便于后续统一或复用取消交互样式。

#### 4.1.5 BatchExtractionManager（核心新增类）

```
BatchExtractionManager（单例）
 ├─ Map<Long, BatchExtractionTask> tasks   // key = projectId
 ├─ submitTask(Project, SheetData, List<ExtractionUnit>, options, customElements)
 ├─ getProgress(projectId) → {state, total, done, failed, currentUnit,
 │                            skipped, startedAt, error}
 ├─ cancel(projectId)
 └─ 内部 BatchExtractionTask implements Runnable
     ├─ ExecutorService workers（共享池，并行度默认 2，可配置）
     ├─ 逐件提交 → CompletionService 收集结果
     ├─ appendRow(): synchronized(sheetData){ rows.add(row); }
     │   → project.update() → 节流 save
     └─ 完成时: 强制 save, state=completed / partial / completed-with-failures
```

要点：
- **行追加与保存的并发安全**：以 SheetData 对象为锁；`GetRowsCommand` 分页按下标访问，追加尾部不破坏遍历一致性；如实现中发现必要，rows 可替换为 `CopyOnWriteArrayList`（读多写少）——编码阶段定。
- **失败隔离**：单件异常只影响该行（提取状态=失败，原因写入状态列），继续后续单元。
- **重试**：单件失败自动重试 1 次（可配置）；仍失败落失败行。
- **案卷汇总行**（后续版本）：卷内最后一件落表 → `generateVolumeSummaryRow()`（题名 llmAnalyze 概括 + 责任者/自定义列去重合并）→ appendRow()。

#### 4.1.8 评审意见（后端实现）

**【R-09｜P1】任务生命周期与资源回收未定义**
- 问题：`BatchExtractionManager` 以 projectId 为键持有任务与进度（含失败列表、当前单元），但未定义：① 项目被删除/重命名后任务的终止与清理；② 任务完成后 tasks 条目是否保留（保留将随运行时长累积内存）；③ 单 JVM 同时运行的提取任务数上限。

- 建议：确认 `ProjectManager.save` 的加锁与去重语义；实现"单写线程 + 请求合并"避免并发写；对 1000 行规模做保存耗时实测，据此调整节流阈值。

**【R-11｜P1】新增命令的注册与访问校验未说明**
- 问题：4.1.6 新增 `get-extraction-progress`、`cancel-extraction`，但未说明注册位置（module/MOD-INF/controller.js 中 Command 注册与 URL 前缀）以及跨项目访问时的项目存在性校验（避免任意 projectId 探测）。

### 4.3 自定义提取类型与 AIMP 接口

#### 4.3.1 请求扩展

沿用 `POST /extract/upload`（multipart），在现有 `file / key_list / sync` 基础上新增：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| custom_elements | String(JSON) | 否 | 自定义类型数组，`[{"key":"custom_1","name":"身份证","action":"include","description":"提取文中出现的身份证号码"},{"key":"custom_2","name":"证据","action":"exclude","description":""}]`（R-13 定稿：`key` 为稳定 ASCII 标识，results 以 key 返回；`name` 仅用于提示词展示） |
| page_count | 响应字段 | — | 响应新增可选字段（PDF 页数；图像=1） |

> AIMP 现状核查（见 4.8）：`/extract/upload` 服务端签名为 file/keys/options（无 custom_elements、无 page_count），且现存与 Java 客户端的契约断裂（key_list/sync 字段名、顶层 results 缺失）——4 项改造详见 4.8.2。**不新增接口**。

#### 4.3.2 AIMP 端提示词组装约定（AIMP 侧实现）

```
基础提示词（现有4要素）按 key_list 生成，之后：
对每个 include 类型（按序）：
  追加指令: "除上述要素外，另请提取以下要素：<name>" + (description 非空时附说明)
对每个 exclude 类型（按序）：
  追加指令: "提取与输出中请忽略/排除以下内容：<name>" + (description 非空时附说明)
输出要求: include 类型结果以其 <key> 为 key 放入 results（key 与传入原样一致，禁止翻译/改写）；
         exclude 类型不得出现在 results 中。
```

#### 4.3.3 OpenRefine 端处理

- include 类型 → 动态列（D-10），行组装时 `row[列名=name] = results.get(key)`（R-13 定稿：OpenRefine 维护 列名↔key 映射；`AimpLlmClient` 现有 map 机制直接支持）；
- include 类型在 results 中缺失 → 该列空串，不影响状态判定；
- **成文日期规范化**（评审结论 Q-5）：AIMP 返回 `date` 后由 OpenRefine 统一解析并规范化为 `yyyy-MM-dd`（支持"2024年3月5日""2024.3.5""2024/03/05"等常见格式）；无法解析时保留 AIMP 原文；
- **排除类型与基础要素同名**（评审结论 Q-10）：照常传递给 AIMP，对应固定列保留但取值恒为空，UI 说明后果；
- 自定义类型结果参与"部分提取"状态判定：基础 4 要素全部为空且自定义列也为空 → 状态"失败"。

#### 4.3.4 兼容性

- AIMP 未升级时：不传或忽略 `custom_elements`（AIMP 端按 4 要素返回），自定义列将为空，**备注列**标注"自定义要素未提取"（R-02 定稿）；`page_count` 缺失按 4.4.3 回退并在备注列标注。

#### 4.3.5 评审意见（AIMP 契约）

**【R-13｜P0】中文类型名作 results key 的契约风险**
- 问题：4.3.2 约定 include 类型"以 `<name>`（中文，如"身份证"）为 key 放入 results"。由 LLM 生成 JSON 并以中文作 key 存在漂移风险：同义替换（"身份证号"/"身份证号码"）、被翻译、缺省、多类型 key 合并，任一发生都会导致 OpenRefine 侧取值失败（表现为静默空列，难以发现）。
- 影响：自定义提取功能可用性不达标，且失败静默（无异常、无状态提示）。
- 建议：契约改为**稳定 ASCII key**——include 元素携带 `key`（如 `custom_1`、`id_card`），请求与响应统一使用 key；中文列名与 key 的映射由 OpenRefine 侧维护；如需 AIMP 组织提示词可另传 `display_name`。
- **【闭环｜2026-09-17｜v1.6】按建议定稿**：请求携带稳定 key、results 以 key 返回、列名↔key 由 OpenRefine 维护（见 4.3.1/4.3.2/4.3.3）。
- 闭环要求：与 AIMP 侧确认 key 约定，同步修订 4.3.1/4.3.2/4.3.3，并补充测试用例（中文名、含空格/括号/斜杠等特殊字符、多类型同义场景）。

**【R-14｜P1】页数双来源口径不一致**
- 问题：4.4.3 folder 用本地图像文件数、pdf 用 AIMP `page_count`。① 同类数据口径不一致，可能因实现差异得出不同页数；② folder 内若含多页 tif，文件数与实际页数不符。
- 建议：统一以 AIMP 返回的 `page_count` 为准（要求 AIMP 对 folder 单元同样返回页数，其转图阶段已知），本地统计仅作 AIMP 未就绪时的兜底并在备注中标注来源。

**【R-15｜P1】超时、重试幂等与资源回收**
- 问题：NFR-2 单单元超时 120s、AIMP 侧单文件处理超时 60s；多页大 PDF（如数百页）OCR 耗时可能超过 120s，将被判定失败并重试；重试无幂等约定（AIMP 侧是否产生重复任务、超时后临时资源是否回收均未说明）。
- 建议：① 按单元规模（页数/文件大小）动态设置读超时，或对大单元直接使用 AIMP 异步任务接口（`batch_extract` + 任务轮询，D-7 已列为后续优化项，可提前用于大单元）；② 明确重试幂等语义与超时后的连接/临时文件回收；③ 区分"超时类失败"与"内容类失败"，便于用户判断是否值得重试。

**【R-16｜P2】AIMP 错误分类缺失**
- 问题：现有 `AimpLlmClient` 仅区分 HTTP 200 与 `success=false`，无错误码契约，OpenRefine 无法区分"AIMP 不可用/格式不支持/OCR 失败/LLM 失败"，只能统一记失败。
- 建议：约定错误码（如 `UNAVAILABLE`、`UNSUPPORTED_FORMAT`、`OCR_FAILED`、`LLM_FAILED`），并映射到状态/备注列与"是否自动重试"策略。

**【R-25｜P2】"部分提取"判定条件未定义**
- 问题：4.3.3 仅定义"基础 4 要素全空且自定义列全空 → 失败"，未定义"部分提取"的判定条件。
- 建议：明确判定规则，例如"存在任一要素为空但至少一项有值 → 部分提取"，并在备注列记录缺失要素清单，便于复核聚焦（与 R-02 备注列方案联动）。

### 4.7 案卷模式设计（法院场景，**首要实现目标**，r3）

> 本节为案卷模式的**权威设计**。与 1.3 U-7、4.2、10.3 中"案卷降级为后续版本"的旧表述冲突时，以本节及 0.7.2 为准。

#### 4.7.1 适用场景与目录形态

- **场景**：法院案卷——根目录下每个文件夹为一个案卷，案卷内含大量案件材料图片，需分门别类著录。
- **层级**：根目录 → 案卷文件夹 → 图片序列（或 PDF 序列）。
- **内容约束**（R-29）：同一案卷内**不混合**类型，默认全部为图片或全部为 PDF。
- **输出形态**（R-28）：本期**仅著录卷内目录（件级信息），不生成案卷汇总行**；案卷号取案卷文件夹名称。

#### 4.7.2 分件机制：标题驱动自动分件（R-27）

- **依据**：按提取到的文件标题为主判断一件是否结束（"通过标题、格式等自动分件"）。
- **流程**：
  1. 案卷内文件按**文件名自然排序**形成卷内页序（1..N）；
  2. 逐页（逐文件）调用 AIMP 提取该页标题及要素；
  3. Java 端按页标题分组：与当前件标题**归一化后相等或相似度 ≥ 阈值**（默认 0.9）→ 归入当前件；标题变化且非空 → 开启新件；
  4. 空标题页固定归入**前一件**（R-30 定稿，不做配置项）；
  5. 每件生成一行：题名取件内**首个非空标题**；责任者/文号/成文日期取件内**首个非空值**。
- **归一化**：去首尾空白、全角/半角统一、去标点、忽略大小写。
- **兜底**：整卷标题全为空 → 整卷作为一件，提取状态标注"分件失败（无标题）"；相邻页标题均不同导致分件过碎时，备注列提示"分件疑似过碎"。

#### 4.7.3 输出列结构（卷内目录）

| 序 | 列名 | 取值 |
|----|------|------|
| 1 | 案卷号 | 案卷文件夹名称 |
| 2 | 件号 | 卷内 3 位自增（`001`、`002`…） |
| 3 | 起止页号 | 件在卷内的页号区间，页号 4 位自增（如 `0001-0005`） |
| 4 | 页数 | 件内页数（即起止页号区间长度） |
| 5 | 题名 | 件标题（LLM 提取） |
| 6 | 责任者 | LLM 提取 |
| 7 | 文号 | LLM 提取 |
| 8 | 成文日期 | LLM 提取，规范化 `yyyy-MM-dd` |
| 9 | 文件夹路径 | 案卷文件夹绝对路径 |
| 10 | 提取状态 | 枚举：成功 / 部分提取 / 失败 / 已取消（R-02 定稿：仅存枚举） |
| 11 | 备注 | 失败原因、页数未知、日期未规范化、自定义要素未提取、分件过碎等 |
| — | 自定义"增加"列 | 插在"提取状态"之前 |

- 与案件模式差异：案卷模式含**案卷号、起止页号**，不含"文件夹名"列；件号为 3 位。

#### 4.7.4 提取单元与 AIMP 交互

- **单元定义**：**页级单元**（单张图片或单个 PDF 各自先提取标题），再由 Java 端按 4.7.2 分组为件。
- **交互**：复用 `POST /extract/upload` 逐页提交；并发度受 NFR-2 约束（默认 2）。
- **页数**：图片=1 页/文件；PDF 取 AIMP `page_count`（与 4.4.3 口径一致）。
- **性能优化（后续）**：由 AIMP 一次返回案卷内页级标题数组以减少调用次数（与 R-15 大单元优化合并考虑）。

```
扫描根目录：
  子文件夹 V → 案卷 V
    V 内文件（图片或 PDF，按文件名自然排序）→ 卷内页序 1..N
    无有效文件的卷 → 跳过并计入"已跳过"计数
```

- 模板：启用 `BATCH_TITLE_VOLUME`（列结构见 4.7.3）。

#### 4.7.6 前端

- "提取模式"单选启用**案卷**（不再置灰）；

#### 4.7.7 分件细节参数（R-30 定稿）

| 1 | 请求字段兼容 | 服务端现签名 `keys: str = Form(...)`（必填）+ `options`（L920-923），而 Java 客户端发送 `key_list`（逗号分隔字符串）+ `sync`（AimpClient L249-255、AimpLlmClient L61-66）→ **现状调用必然 422**；需在服务端兼容 `key_list`（逗号分隔转列表）与 `sync`（忽略） | **契约修复** |
| 2 | 响应结构兼容 | 现 `results` 嵌于 `data` 内（pipeline_manager L549/692/794），Java 客户端在顶层解析 `results`/`extracted_fields`（AimpClient L291-305、AimpLlmClient L84-87）→ **现状静默空结果**；需将 `results` 提升至顶层（Java 端零改动） | **契约修复** |
| 3 | custom_elements 透传 | 新增可选 Form 参数（默认 `[]`，不传时行为不变）；解析与提示词组装复用 `/extract/archive` 已有逻辑（L92-99、L966-1009） | 新能力 |
| 4 | `page_count` 响应字段 | 响应新增可选字段（PDF 页数；图像=1）；旧客户端忽略未知字段 | 新能力 |

- 案卷模式页级提取：逐页（单图）调 `/extract/upload`，能力覆盖；
- 性能优化（后续）：复用 `/batch/extract` + 任务轮询作为页级批量通道，无需等新接口；
- R-22（stub）：按 4 项改造同步扩展模拟范围（key_list 兼容、顶层 results、custom_elements 回显、page_count）。

#### 4.8.4 对 data-quality 现有功能影响核查（r3.1）

| data-quality 调用路径 | 是否受改造影响 | 说明 |
|------------------------|----------------|------|
| `testConnection` → GET `/health`、`/docs` | 否 | 不在改造范围 |
| `batchCompare` → POST `/extract/archive/batch_compare` | 否 | 不在改造范围 |
| `llmAnalyze` → POST `/api/llm/analyze` | 否 | 不在改造范围 |
| 7999 独立端点（/blank /stain /rectify /dpi /bitdepth /jpeg/quality 等）、7998 `/api/ocr/extract`、`/inspect` 系列 | 否 | 不在改造范围 |
| `AimpClient.extractContent()` → POST `/extract/upload` | 否（且属死代码） | 全 src 检索无调用方（仅 AimpClient.java L211-221 定义）；即便改造，#3/#4 为可选参数/响应字段，向后兼容 |

结论：**本次改造对 data-quality 现有功能零影响**（#3/#4 均为可选字段，向后兼容）。核查同时暴露 `/extract/upload` 现存契约断裂（#1/#2），必须随本次一并修复，否则 FilesExtension 对接该端点不可用。

#### 4.8.5 对 4.3 契约的影响

- 4.3.1 请求扩展维持（custom_elements 带 key + page_count 响应字段）；请求侧统一为 **`key_list`（逗号分隔字符串）**，AIMP 端兼容转换（4.8.2 #1）；
- key 约定见 4.3.2（R-13 定稿：稳定 ASCII key，results 以 key 返回）；
- 响应顶层结构约定：`{success, data, results, page_count?, task_id, message, processing_time}`（results 顶层提升，见 4.8.2 #2）。

## 5. 错误处理

| 场景 | 处理 |
|------|------|
| AIMP 不可用（创建前预检失败） | 阻止创建，弹窗提示"AI服务模块不可用，请检查或重启模块"（国际化键 `files-extension/aimp-service-unavailable`） |
| 提取中 AIMP 中断/超时 | 单件重试 1 次 → 仍失败落失败行（状态列含原因），任务继续；连续 N 个（默认10）失败暂停任务并警示 |
| 目录在提取中被删除/文件不可读 | 该单元失败落表，任务继续 |
| 页数未知（PDF 无 page_count） | 页数=1，状态列标注"页数未知" |
| 单元数超上限（NFR-6） | 创建前拦截提示分批 |
| 自定义类型名与固定列重复/互相重复/为空 | 创建前校验失败，返回具体违规项，不创建项目（FR-15） |
| 自定义 include 类型数量超上限（NFR-7） | 创建前拦截提示 |
| 排除类型与基础 4 要素同名（如排除"文号"） | **允许传递**（评审结论 Q-10）：AIMP 按指令忽略该要素，OpenRefine 对应列保留但值恒为空 |
| AIMP 不识别 custom_elements（旧版本） | 自定义列为空，状态列标注"自定义要素未提取"，任务整体不中断（4.3.4） |
| 成文日期无法解析为标准格式 | 保留 AIMP 原文返回值，状态列标注"日期未规范化" |
| 扫描结果为 0 件 | 创建前提示"未发现可提取的件（需包含图像/PDF的文件夹或PDF文件）"，不创建项目 |

### 5.1 评审意见（错误处理）

**【R-20｜P1】连续失败暂停后无恢复路径**
- 问题：第 5 节"连续 N 个（默认10）失败暂停任务并警示"未定义恢复方式（无 resume 命令、前端无入口），任务将永久停留在暂停态，用户只能重新创建项目。
- 建议：新增 `resume-extraction` 命令（从暂停点继续，跳过已落表单元）或前端提供"继续/重跑失败"按钮；进度返回需含 paused 状态与暂停原因（如"连续 10 件提取失败，疑似 AIMP 不可用"）。

**【R-21｜P1】重跑口径前后不一致**
- 问题：1.4 FR-11 表述"本期降级为工具栏全量重跑"，而 10.1 Q-8 结论为"本期工具栏'重跑失败行'"。两者对实现范围与成本影响显著（按行定位重跑需额外的行级接口与状态映射）。
- 建议：统一为"本期提供全量重跑（重新扫描目录并重新填充），行级/失败行重跑列入后续版本"，并同步修订 FR-11 与 Q-8 的表述。

## 9. 风险分析

| 风险 | 缓解 |
|------|------|
| 增量追加与用户编辑/持久化并发冲突 | 锁策略（D-1）+ 提取中禁列操作（D-6）；必要时升级 CopyOnWriteArrayList |
| AIMP 吞吐不足导致长任务 | 并发度可配 + 连续失败暂停 + batch_extract 后续优化 |
| 自定义类型导致提示词膨胀/提取质量下降 | include 数量上限（NFR-7）+ description 引导 + 状态列可观测（部分提取） |
| 自定义类型结果 key 与列名不一致（AIMP 实现偏差） | 4.3.2 明确约定 key=name 原样返回；联调用例覆盖 |
| 件号名称解析不符合部分目录命名（如名称无数字） | 回退扫描顺序号 + 预览提示；后续版本提供 sequence 等模式 |
| 排除同名基础要素造成该列恒空 | UI 说明后果（评审结论 Q-10 已接受） |
| 进度轮询增加服务端压力 | 轻量只读进度对象，2s 间隔可接受 |
| 大项目持久化 IO | 节流保存（NFR-4）+ 全局定时保存兜底 |
| 用户提取中途导出/关闭项目 | 节流保存保证已落表数据安全；任务后台继续，重进项目可见进度 |
| 与第一版同步提取功能并存造成理解混乱 | 模板并存、默认新模板（Q-2 维持建议） |
