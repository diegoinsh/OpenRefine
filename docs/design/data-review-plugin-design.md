# 数据校审模块插件设计（Data Review Plugin）

> 版本：v0.2（2026-10-29，评审决策已合并）
> 状态：评审通过，Stage 1 开发启动（分支 `data-review`）
> 参考形态：合规审查插件（moduleCode=inspection，狗模块号 3）——本模块为其之后的第二个基于 RCP+Solon 插件架构的业务插件

---

## 1. 背景与定位

### 1.1 业务背景

政企业务流程中存在大量对文书、材料内容的校对与核验审定需求：审批材料、合同材料、各类归档材料等。当前已具备：

- **文件提取能力**（FilesExtension / files-engine）：件/卷两级结构化提取（OCR + LLM），产出著录数据；
- **合规审查能力**（data-quality / inspection）：面向档案合规的规则检查（18 类规则），有成熟的规则配置 UI 与结果展示页。

"数据校审"是在两者之上的新业务能力：**对输入的原始文件（版式文件、图像）按用户定义的校审规则做内容级、语义级校对核验，产出带证据定位的校审结果**，并通过界面与接口对外提供。

### 1.2 与合规审查的边界

| 维度 | 合规审查（inspection） | 数据校审（本模块） |
|---|---|---|
| 目标 | 档案/数据是否符合管理规定（偏归档合规） | 材料/文书内容是否正确、完整、合规（偏业务核验） |
| 规则来源 | 系统预置为主（四性检测、格式、图像质量等 18 类） | 用户自定义为主（按业务场景组合规则集） |
| 检查对象 | 项目数据 + 图像 | 原始文件本身（件/卷两级），含未著录材料 |
| 输出 | 合规检查结果 | 校审结果 + 证据定位（页、区域、OCR 原文、相似度） |

两者共享底层 AI 能力（AIMP：OCR / 印章检测 / LLM）与 UI 形态（统计 + 明细联动），但规则体系、任务编排、结果模型独立。

### 1.3 设计原则

1. **规则驱动**：所有校审项都是规则实例，规则可配置、可分组、可复用为"校审方案"；
2. **证据可溯**：每条结果必须携带证据（所在件/页、区域框、OCR 原文、比对差值），点击可联动原图；
3. **件/卷两级**：与现有提取场景一致——卷级汇总 + 件级明细，同一材料既可按件校审也可按卷校审；
4. **能力分层**：程序规则（正则/白名单/数值）零成本优先，图像检测与 LLM 语义判断按需调用，控制成本与速度；
5. **架构同源**：走 RCP + Solon 插件架构（capability-platform SPI），OR 内仅承载 UI 垫片，不新增 butterfly 依赖。

## 2. 校审规则分类体系

综合用户需求与业界实践检索结论，规则分为 **5 大类**。业界参照：

- 智能合同审查通用三范式：**一致性审查 / 完备性审查 / 风险点审查**（群杰合约卫士等）；
- 智能签署核对三能力：**关键信息一致性校验 / 格式合规性审查（骑缝章、页码连续、签章位置）/ 授权合规核验**（WPS 黑马校对）；
- 档案四性检测（DA/T 70—2018《文书类电子档案检测一般要求》）：真实性、完整性、可用性、安全性——本分类可完整映射（见 2.6）。

### 2.1 存在类（presence）

判断某要素/特征**是否存在**于指定材料或指定区域。

| 规则项 | 说明 | 检测手段 |
|---|---|---|
| 印章存在 | 落款章、骑缝章、专用章（公章/合同章/财务章）区分 | 图像印章检测（AIMP） |
| 签字存在 | 指定区域是否有手写签名；手写 vs 印刷区分；签章文字 | 图像手写检测 + 区域限定 |
| 指纹存在 | 区别于印章的红色/黑色指纹印痕 | 复用 AIMP 印章检测（yolo.pt）+ **后处理区分**（印章与指纹易混淆：按颜色饱和度/纹理/边缘几何特征二次判别，详见 5.1） |
| 要素存在 | 某字段/条款/字样是否出现（如"违约责任"条款） | OCR + LLM / 正则 |
| 材料存在 | 某件是否存在、某页是否存在（缺件、缺页） | 件级清单比对 |
| 附件存在 | 声明的附件是否随附（正文写"附件 2 份"） | LLM 语义 + 清单核对 |

### 2.2 一致性比对类（consistency）

两个来源的取值是否一致，**输出量化差异**（相似度百分比、数值差）。

| 规则项 | 说明 | 输出 |
|---|---|---|
| 签名 vs 要素 | 签名字迹（OCR）与某著录要素（如责任者/当事人）是否一致 | 相似度 % |
| 印章 vs 要素 | 印章文字与责任者/主体名是否一致 | 相似度 % |
| 大小写一致 | 金额大写与小写是否相符 | 数值差 |
| 跨件一致 | 同一要素在不同件间取值是否一致（如两份合同主体名） | 差异明细 |
| 日期逻辑 | 签署日期 ≥ 合同日期、落款日期 ≤ 归档日期等时序校验 | 差值天数 |

### 2.3 规范类（compliance）

内容是否符合明文规定。

| 规则项 | 说明 | 检测手段 |
|---|---|---|
| 条款完备 | 必备条款是否缺失（权利义务、违约责任、争议解决等） | LLM 语义 |
| 取值规范 | 字段取值在允许枚举内（如保管期限 ∈ {永久, 30年, 10年}） | 程序白名单 |
| 格式规范 | 日期、档号、证件号等格式正确 | 正则 |
| 行为合规 | 开票者资质违规、开票内容违规、超权限审批等 | 规则引擎 + LLM |
| 顺序规范 | 材料排列/流程顺序是否符合规定 | 件序比对 |

### 2.4 名单类（list）

| 规则项 | 说明 |
|---|---|
| 黑名单 | 材料中主体/内容命中黑名单（违约主体、违规开票者、敏感词） |
| 白名单 | 主体必须在白名单内（合格供应商名录等） |

名单数据独立管理（导入/维护界面），规则只引用名单名称。

### 2.5 逻辑勾稽类（logic，可并入 2.2/2.3，单列便于扩展）

跨件、跨字段的勾稽关系：份数与清单相符、页数与目录一致、金额分项合计 = 总额等。

### 2.6 与档案四性检测的映射（预置模板）

| 四性 | 对应规则类 |
|---|---|
| 真实性 | 存在类（章/签/指纹）+ 一致性类（章文 vs 责任者） |
| 完整性 | 存在类（缺件/缺页）+ 规范类（条款完备）+ 逻辑类（份数勾稽） |
| 可用性 | 复用合规审查已有图像质量规则（可读性） |
| 安全性 | 复用合规审查已有病毒检测 + 名单类（敏感内容） |

> 即：四性检测可作为**预置校审方案**下发，规则本体来自本分类 + 合规审查已有规则引用，不重复造轮子。

## 3. 总体架构

```
┌─────────────────────────────────────────────────────┐
│ OpenRefine 前端（Solon 外壳 + OR 组件垫片）           │
│  · 校审规则配置页    · 校审任务页    · 校审结果页      │
│  · 复用 file-view-panel 图像定位 / 数据表格组件        │
└──────────────┬──────────────────────────────────────┘
               │ HTTP（平台路由 /datareview/**）
┌──────────────▼──────────────────────────────────────┐
│ ruyi-capability-platform（Solon 容器）                │
│  · 新 Solon 插件 moduleCode=datareview（狗模块号 15） │
│  · CapabilityPlugin SPI：routes() / ui() 注册        │
│  · 规则库/名单库/任务与结果存储（SqliteStorage）       │
│  · 校审任务编排器（规则×件的调度、并发、进度）          │
└──────────────┬──────────────────────────────────────┘
               │ HTTP（AIMP 既有/新增接口）
┌──────────────▼──────────────────────────────────────┐
│ ruyi-aimp（AI 能力层）                                │
│  · OCR（rapidocr）        · 印章/指纹/手写图像检测     │
│  · LLM 语义判定（复用 model_manager 推理通道）         │
│  · 复用 /extract/upload 要素提取，新增 /review/* 校审  │
└─────────────────────────────────────────────────────┘
```

狗模块号 **15**（2026-10-29 评审确认）。

### 3.1 插件接入方式（与 inspection 同构）

依据现状探查（capability-platform SPI）：

- 插件实现 `CapabilityPlugin`：`moduleCode()` 返回 `datareview`，`install(PlatformContext)` 内注册：
  - `routes()`（SolonRouteRegistry）：REST 接口；
  - `ui()`（SimpleUiRegistry / MenuItem）：菜单项——"数据校审"（子项：校审规则 / 校审任务 / 校审结果）；
- `PluginLoader` 以独立 `URLClassLoader` 加载，按 `license().isAuthorized("datareview")` 决定装载，未授权自动隐藏菜单；
- OR 侧 UI 走"Solon 外壳 + OR 组件垫片"（同 inspection 方案）：平台 Shell 页面挂载 OR 的表格、文件预览组件，不依赖 butterfly 模块。

## 4. 数据模型

### 4.1 校审规则（ReviewRule）

```json
{
  "ruleId": "r-20261029-001",
  "name": "落款处必须加盖公章",
  "category": "presence",           // presence | consistency | compliance | list | logic
  "target": {                        // 校审对象
    "scope": "piece",                // piece=件级 | volume=卷级 | page=页级
    "elementType": "公章",            // 存在类的特征类型：公章/合同章/财务章/签字/指纹/...
    "region": {                      // 可选：限定检测区域——双轨（评审确认）：规则配置用相对比例，适配任意分辨率；结果证据用像素 bbox
      "x": 0.6, "y": 0.8, "w": 0.4, "h": 0.2
    }
  },
  "expect": {                        // 期望
    "operator": "exists",            // exists | not_exists | equals | similar | in_list | regex | ...
    "value": null,                   // 期望值/比对源（如 "$责任者" 引用著录要素）
    "threshold": 0.85,               // 相似度阈值（一致性类）
    "listName": null                 // 名单类引用
  },
  "severity": "error",               // error | warn | info
  "enabled": true,
  "remark": ""
}
```

### 4.2 校审方案（ReviewPlan）

规则的有序集合，面向一个档案门类/业务场景的整套校审项（如"合同签署校审方案"）。支持从模板复制、导入导出。**四性检测方案**即预置 Plan。

### 4.3 校审任务（ReviewTask）

```json
{
  "taskId": "t-...",
  "planId": "p-...",
  "source": {
    "mode": "folder",                // folder | orProject
    "rootPath": "D:/.../案卷目录",    // 件/卷两级目录（复用 FilesExtension 目录约定）
    "orProjectId": null
  },
  "status": "running",               // pending|running|done|failed|cancelled
  "progress": { "totalPieces": 26, "donePieces": 12, "totalRules": 40 },
  "createdAt": "...", "finishedAt": null
}
```

### 4.4 校审结果（ReviewResult）

```json
{
  "taskId": "t-...",
  "ruleId": "r-...",
  "ruleName": "落款处必须加盖公章",
  "category": "presence",
  "targetRef": { "volume": "JZ07-2024-M2-0158", "pieceNo": 3, "page": "0005" },
  "status": "pass",                  // pass | fail | warn | unknown（无法判定）
  "evidence": {
    "image": "0005.jpg",
    "bbox": [120, 880, 420, 1050],   // 证据区域像素坐标（点击定位用）
    "ocrText": "……",                 // 证据原文
    "detail": "相似度 92.3%（阈值 85%）",  // 一致性类的量化说明
    "sources": [                     // 多来源时逐条列出（页号升序）
      { "page": "0005", "value": "..." }
    ]
  },
  "checkedAt": "..."
}
```

## 5. 接口设计（平台 REST，前缀 `/datareview`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST | `/datareview/rules` | 规则列表 / 保存（单条） |
| POST | `/datareview/rules/batch` | 批量保存/导入（JSON/Excel） |
| GET/POST/DELETE | `/datareview/plans` | 校审方案 CRUD |
| GET/POST/DELETE | `/datareview/lists` | 黑白名单管理（平台界面维护 + 接口导入，与合规审查/批量提取的名单类数据同模式） |
| POST | `/datareview/tasks` | 创建校审任务（plan + source） |
| GET | `/datareview/tasks/{id}` | 任务状态与进度 |
| POST | `/datareview/tasks/{id}/cancel` | 取消任务 |
| GET | `/datareview/tasks/{id}/results` | 结果明细（分页、按件/规则/状态过滤） |
| GET | `/datareview/tasks/{id}/summary` | 统计汇总（结果页顶部统计） |
| GET | `/datareview/tasks/{id}/export` | 导出（Excel） |
| POST | `/datareview/aimp/test` | AIMP 连通性测试（复用合规模式） |

### 5.1 AIMP 侧接口

| 接口 | 状态 | 说明 |
|---|---|---|
| `/extract/upload` | **复用** | OCR + 要素提取（页级文本/要素），一致性类、规范类所需 OCR 文本由此获取 |
| `/review/element`（新增） | 设计 | 图像特征检测：入参图片 + 检测类型（公章/签字/指纹/骑缝章）+ 可选区域 → 返回存在性、位置 bbox、印章 OCR 文字。印章检测复用现有 yolo.pt 模型 |
| `/review/llm`（新增） | 设计 | 语义判定：入参 OCR 文本 + 判定指令（条款存在/违规判断）→ 返回结论 + 依据（复用 model_manager 推理通道与 JSON 输出规约） |

**指纹/印章区分后处理**（评审确认的现状与对策）：AIMP 已有印章检测能力（yolo.pt 模型），但指纹与印章（尤其红色指纹/椭圆章）易混淆。对策为**检测出之后加后处理二次判别**，在 `/review/element` 内实现、不引入新模型：

1. 颜色特征：印章多为均匀红色（朱红/印泥），指纹红色浅且纹理呈嵴线（平行细纹）；
2. 纹理特征：局部二值模式（LBP）/方向梯度统计——指纹有规律嵴线纹理，印章为实心或空心线条+文字；
3. 几何特征：印章外形规则（圆/椭圆/矩形边框），指纹为不规则椭圆且长宽比偏大、边缘毛糙；
4. 判别输出置信度不足时降级为"印痕存在（类型未知）"，结果状态标 `unknown`，由人工复核。

> AIMP 改造评估：图像检测能力与 data-quality 的图像检查器同源（AIMP 已有图像检测基础），新增的主要是"带区域限定 + 类型细分"的检测入口与统一返回结构；LLM 判定复用现有推理与提示词管理机制，无新增模型依赖。

## 6. UI 设计

### 6.1 菜单结构

```
数据校审
 ├── 校审规则        （规则 CRUD、按分类分组、方案管理）
 ├── 校审任务        （发起任务：选方案 + 选来源目录/项目，进度条同批量提取）
 └── 校审结果        （统计 + 明细）
```

### 6.2 结果页（参照合规审查结果页形态）

- **顶部统计区**：总检查项 / 通过 / 不通过 / 警告 / 无法判定，卡片可点击，点击即过滤下方明细；
- **明细区——卷级/件级分两个 Sheet 展示**（评审确认）：与批量提取"卷级条目 + 件级条目"的数据页组织一致，校审结果在 OR 项目数据区域分 **两个 Sheet**：
  - `校审结果-卷级`：行 = 卷级校审结果（按卷聚合：档号、卷内规则命中统计、最差状态、卷级规则明细）；
  - `校审结果-件级`：行 = 件级校审结果（件号、页、规则名、分类、状态、说明），单元格点击 → 右侧 `file-view-panel` 打开证据图并按 bbox 高亮定位（复用现有"要素点击定位到页"能力与页码 chips 翻页）；
- 状态色：通过=绿 / 不通过=红 / 警告=黄 / 无法判定=灰；
- 支持导出 Excel（所见即所得：两个 Sheet + 统计 + 证据页码）。

### 6.3 结果写入 OR 项目数据区域（评审决策 Q-5）

校审任务的数据来源**没有"著录条目"这一项**（不同于批量提取先产条目再展示的链路），因此校审结果**直接写入 OR 的项目数据区域**：

- 任务创建时即建立 OR 项目（或复用既有项目），先建 `校审结果-卷级`、`校审结果-件级` 两个 Sheet 的空表头；
- 校审执行过程中结果逐条/逐件写入对应 Sheet（复用批量提取"空项目增量填充 + 横幅进度"的成熟机制，含 ExtractionChangeGuard 只读守卫）；
- 平台侧 Sqlite 结果库仍保留全量明细与证据（bbox/OCR 原文/多来源），OR 数据区域只承载展示列；bbox 定位等富证据通过平台 `/datareview/tasks/{id}/results` 接口按需查询。

## 7. 校审执行流程

```
创建任务 → 扫描目录（件/卷结构解析，复用 UnitScanner 逻辑）
   → 逐件编排：件首页/末页强制检测（存在类必须页）
             + 规则声明的目标页/区域
   → 能力分层执行：
       ① 程序层（正则/白名单/清单比对/数值）——零 AI 成本，先跑
       ② 图像层（章/签/指纹）——仅对需要页调用 AIMP 检测
       ③ 语义层（LLM）——仅对 ①② 无法判定的规则调用
   → 结果落库（SqliteStorage）+ **写入 OR 项目数据区域**（卷级/件级两个 Sheet，见 6.3）
      → 前端轮询进度（复用批量提取的进度推送与横幅模式）
   → 卷级 Sheet 汇总行（按卷聚合最差状态 + 数量统计）
```

性能要点：延续批量提取经验——页级缓存（ExtractionPageCache 同款思路）、件首末强制 + 中间页按需、LR 跳页预筛不适用于校审（校审必须覆盖指定页），但 OCR 结果与提取任务可共享缓存，同目录二次校审近乎零 OCR 成本。

## 8. 实施计划
